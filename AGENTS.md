## AI Delivery Contract v1 — ENX Power mandatory local execution (2026-10-26)

This is the repository-local application of the existing canonical policy in `enxpower/group-governance/docs/AI_DELIVERY_CONTRACT.md`. It applies to **all new, resumed, coding, documentation, deployment and maintenance tasks** in this repository. This self-contained section works without access to the private central file. Existing project-specific business, safety, security, finance, confidentiality, assessment, publishing, branch and R3/Owner controls remain fully authoritative; this grants no new write or merge permission.

**Six non-negotiable rules:** **business outcome** before technology; **scope freeze** (no unauthorized extras); **mature reuse** before reinvention; **bounded task** with stop/retry budget; **independent verification** of actual acceptance; **release seal** and STOP when authorized gates pass.

### ANTI-DRIFT STOP GATE
Before each substantive action: **original approved goal → one unmet original acceptance criterion → smallest necessary action → affected/Do Not Touch boundary → independent evidence**. No direct causal link: do not execute. If Owner reports drift, stop unrelated work immediately and return to the original goal, not more plans, tool installation, refactoring or parallel projects. Two evidence-free retries trigger re-triage. `commit != CI != merged != deployed != user verified != accepted`; VWS Completed records externally verified results only.

### Documentation fast lane / GitHub Actions proportionality
For ordinary R0 non-executable/non-authoritative notes, typos or explanations: **one permitted edit + readback**, without creating ceremonial Issue→PR→CI→Actions→deployment→VWS loops. This never bypasses existing protected branches, required checks or publication controls. A Markdown change affecting contracts, approved specifications, legal/accounting truth, public publishing input, security, CI or governance is **not** automatically R0. Code uses relevant tests/mandatory checks; production changes and R3 decisions retain their actual protections. Do not introduce or disable Workflows merely to satisfy an adoption marker.

## Authority and workflow

Within the approved product, budget, environment, and system boundaries, routine technical work is standing-authorized through:

`Issue/task → branch → implementation → tests → PR/review → merge → reversible existing-environment deployment → live verification → rollback when needed → VWS`.

Use required checks and repository-local review. Do not pause for a ceremonial Owner signature when gates pass. Escalate only an R3 Owner-decision exception in `docs/STANDING_ENGINEERING_AUTHORITY.md`.

## Non-negotiable protections

- Preserve repository-specific product, architecture, safety, privacy, finance, transaction, legal/tax, credential, permission, destructive-action, and public-communication controls.
- Never weaken tests or hide failures to obtain green status.
- Never expose secrets or sensitive data.
- Keep changes focused, auditable, and reversible.
- Verify actual live behavior; `merged != deployed != verified`.
- Only externally verified facts enter VWS Completed.

Older repository wording that requires separate Owner approval for routine PR creation, merge, deployment, publication, or already-approved scheduled execution is superseded by the standing policy. True R3 business/authority exceptions remain Owner decisions.

## AI Delivery Contract v1 — AdSense Insights Workstream

This existing repository adopts the group-wide six-rule delivery overlay for the active AdSense workstream. Read `enxpower/group-governance/docs/AI_DELIVERY_CONTRACT.md` and `docs/GLOBAL_OBJECTIVE_LOCK.md` when accessible. The following local rules remain binding even if the private group repository is inaccessible.

1. **Business outcome first:** use Issue #5 as the approved goal and `docs/VERIFIED_WORKING_STATE.md` as the evidence-backed progress pointer. Optimize for verified website usability and AdSense policy readiness, not number of commits.
2. **Freeze scope:** keep existing corporate identity, unrelated business systems, DNS, credentials and billing unchanged. Reject unrelated redesign, speculative new platforms and release-gate inflation.
3. **Reuse before building:** preserve existing site technology and published brand assets; consume existing governed intelligence via a narrow approved content contract. Do not rebuild a CMS or publisher.
4. **Bound each change:** one issue-linked, reversible PR per meaningful acceptance gate; identify diff scope, evidence, risks, rollback and stopping condition. After two evidence-free retries, reassess rather than repeat.
5. **Verify independently:** enforce English-only active project text (including code comments), source provenance and public-safe material; test calculations, mobile and desktop behavior, and live URLs. Treat merged, deployed, and verified as separate states.
6. **Seal on actual acceptance:** complete required accessibility, security, privacy, publisher-policy and live release gates, then stop optional improvements. Google alone determines AdSense approval.

**Authority and advertising restrictions:** Existing R0–R3 authority, repository-specific protections and genuine Owner exceptions remain in force. Unreviewed or uncurated machine-generated reports are ad-free by default; automation is not an AdSense policy exemption. Do not silently enable site-wide automatic ads on such pages. No customer/private material, secrets, or unverified company claims may be released.
