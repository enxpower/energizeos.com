System Design

Separate recommendation from control.

The architecture places analysis and decision support above a deterministic supervisory EMS. Customer applications can be designed around auditable site models and scoped requests, while actual power-system commands remain within the authorized EMS and protection stack.

Application Domains

Decisions worth explaining.

01 / SITE OPERATIONS

Why did the system respond this way?

Connect timestamped dispatch decisions with site load, meter data, alarms, breaker positions and operating constraints. Traceable evidence is more useful than an answer without its source.

02 / VALUE ANALYSIS

What created the performance gap?

Compare the expected tariff or market value of a feasible schedule against metered results. Separate demand peaks, battery derating, availability, forecast error and export limits before attributing a financial difference.

03 / DISPATCH OPTIONS

Which operating plan remains feasible?

Rank candidate charging and discharging windows against energy capacity, PCS power limits, state-of-charge reserve, site demand and utility interconnection rules. A proposed plan still requires deterministic validation.

04 / HEALTH AND FAULTS

What should an operator investigate?

Interpret battery alarms, temperature trends and constraint changes alongside manufacturer-defined limits. A diagnostic explanation must never silently acknowledge faults or remove a protective lockout.

Integration Design Reference

A microgrid is a collection of site-specific constraints.

A scalable software service needs a consistent view of the site without treating every installation as interchangeable. The following entities form a practical integration design reference. They describe the information an implementation would need; they are not live API endpoints or a published customer SDK.

Planning is not field execution

An optimization result can estimate energy movements, expected savings and operating risk. It cannot prove a site will follow the plan until interlocks, data quality, control permissions and real physical constraints have been verified.

Isolation is an essential service property

Customer-facing integrations require per-site authorization, authenticated back-end access, bounded usage, audit records and explicit operational responsibility. Client-side exposure of model credentials is not an acceptable integration design.

Engineering Sequence

From reference model to trusted site operation.

  1. Define the operating envelope. Record the electrical topology, protection behavior, constraints and utility requirements before optimizing a schedule.
  2. Reconcile site data. Validate measurement units, timestamps, mapping accuracy, completeness and behavior during communications loss.
  3. Evaluate historical scenarios. Compare advisory outcomes with known site events and explain material errors or unexplained recommendations.
  4. Introduce authorized integration. Apply identity, site permissions, audit trails, rate and cost limits and a tested server-side boundary.
  5. Validate supervised operation. Require documented acceptance tests, deterministic safeguards and rollback before enabling any customer-controlled workflow.

Actual service availability and deployment conditions depend on project-specific engineering and approved integration testing. Architecture descriptions and reference scenarios should not be treated as a customer-access entitlement.
